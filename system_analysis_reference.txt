--------------------------------------------------
SYSTEM OVERVIEW
--------------------------------------------------
Solteira & Brands is an ASP.NET MVC + Entity Framework 6 storefront backed by MySQL/MariaDB (`SolteiraBrandsConnection`). Buyers browse `tbl_products`, manage a per-user `tbl_carts` / `tbl_cart_items`, and place orders into `tbl_orders` with snapshot line items in `tbl_order_items`. Stock is decremented when an order is created. Staff roles (ADMIN, MANAGER, STAFF) approve or reject orders, verify bank/GCash payment proofs in `tbl_payments`, manage courier shipments via `tbl_deliveries`, and record cash-meetup outcomes in `tbl_meetup_outcomes`. Layaway uses `tbl_orders.payment_type = LAYAWAY`, `tbl_layaway_settings`, multiple verified payments, and monthly `payment_deadline` anchors from order creation. Payment deadlines and reminder emails are enforced by `OrderDeadlineService` (timer job). Audit entries go to `tbl_activity_logs`. Authentication is Forms Authentication with roles embedded in the ticket; buyers must complete email OTP verification (`tbl_verification_tokens`) before login succeeds.

--------------------------------------------------
SYSTEM WORKFLOWS
--------------------------------------------------

1. User Authentication Flow
- Registration (`AccountController.Register`): Validates terms, email uniqueness, username rules (max 14, no spaces), password policy (`PasswordValidation`), first/last name. Creates `tbl_users` with BUYER role, `IsVerified = false`, hashes password (`PasswordHasher`). Inserts `tbl_verification_tokens` with `TokenType = EmailVerification` and hashed 6-digit OTP; emails OTP.
- Verify (`VerifyAccount`): Validates OTP hash, marks token used, sets `IsVerified = true`.
- Login (`AccountController.Login`): Checks active user, password, blocks buyers with `IsVerified == false` (returns redirect to verify). Issues FormsAuthentication ticket with `userData = username|ROLE`. Staff with `MustChangePassword` redirect to change-password page (`ForcePasswordChangeFilterAttribute`).
- Logout: Signs out and clears session.
- Profile: `GetMyProfile` / `UpdateProfile` / `UploadProfileImage`; username change sets `UsernameChangedAt` for 30-day cooldown.
- Password reset uses `TokenTypePasswordReset` tokens (same table).

2. Shopping Cart Flow
- `GetOrCreateActiveCart` ensures one `tbl_carts` row with `IsActive` for the user.
- `AddToCart` / `SetCartItemQuantity` / `RemoveFromCart` (and related): Enforce non-archived product, stock limits, merge quantities per product.
- `GetMyCart` prunes archived/out-of-stock lines and caps quantities to `StockQuantity`.
- `CreateOrder` does not clear `tbl_cart_items` in the controller code path shown; clearing is left to the client or a separate step (no server-side cart wipe in `CreateOrder`).

3. Order Processing Flow
- Buyer posts `CreateOrderRequest` with items and checkout fields. Server validates stock, sets `OrderStatus = Pending Approval` (`OrderStatus.PendingApproval`), `PaymentType` from payment method string (Layaway → LAYAWAY; meetup in method → CASH_MEETUP; else FULL), `DeliveryType` MEETUP vs COURIER, decrements `tbl_products.stock_quantity` per line, creates `tbl_order_items`.
- Admin/staff `UpdateOrderStatus`: Pending Approval → Approved (sets `PaymentDeadline` for non-meetup to UTC now + `PaymentDeadlineSettings.DaysToPayAfterApprovalOrResubmit` days; meetup orders get null deadline), or Rejected/Cancelled with optional stock restore via `InventoryReleased`.
- `RevokeApproval`: Approved → Pending Approval only if no payments exist.

4. Payment Flow (including layaway logic)
- Buyer uploads proof → `UploadPaymentProof` → `tbl_images`. `SubmitPayment` creates `tbl_payments` with `PaymentStatus = SUBMITTED`, sets order to `Awaiting Payment Verification`, clears `PaymentDeadline` until admin acts. Meetup scheduling validates date/time window; layaway cannot use meetup cash channel.
- Admin `UpdatePaymentStatus`:
  - REJECTED: stores reason, `AllowResubmit`; if resubmit allowed, resets `PaymentDeadline` (non-layaway: now + days; layaway with verified installments: monthly anchor from `order.CreatedAt` + grace). Order status intentionally stays `Awaiting Payment Verification` for buyer resubmit UX.
  - VERIFIED: Sums VERIFIED payment amounts. Meetup-like orders (`DeliveryType` MEETUP, `PaymentType` CASH_MEETUP, or any verified payment with `MeetupDatetime`): set `RemainingBalance = 0`, `OrderStatus = Ready for Meetup`, insert `tbl_meetup_outcomes` with `READY_FOR_MEETUP` if none. Otherwise: update `RemainingBalance`; if zero → `Paid`, else → `Layaway Active` and for LAYAWAY set next `PaymentDeadline` to `CreatedAt` (as UTC) + verifiedCount months.
- Multiple payments per order are expected for layaway (and theoretically partial full pay paths).
- `OrderDeadlineService.EnforcePaymentDeadlines`: Cancels overdue orders in specific statuses, restores stock once via `InventoryReleased`. Sends reminder emails (full vs layaway lead times from `PaymentDeadlineSettings`).
- UI/admin listing may display order as Cancelled when latest REJECTED has `AllowResubmit = 0` and no newer SUBMITTED payment (display logic in `GetOrders`).

5. Delivery Flow
- Courier: Staff creates/updates `tbl_deliveries` with `DeliveryStatus` PENDING → IN_TRANSIT → DELIVERED (`DeliveryStatus` constants). Order status moves to `In Delivery` / `Completed` per controller rules (e.g. delivered completes order).
- Meetup: After payment verification, order is `Ready for Meetup`; staff may mark meetup outcomes `COMPLETED` (proof required), `NO_SHOW`, or `CANCELLED` via `UpdateMeetupOutcome`; `RescheduleMeetup` from `No Show` to `Meetup Rescheduled`. Additional `tbl_meetup_outcomes` rows and `LogActivity` calls record actions.

6. Admin/Staff Actions
- Role gating: `[Authorize(Roles = "...")]` uses ADMIN, MANAGER, STAFF; storefront buyer actions use `[BuyerAuthorize]` (BUYER only).
- Inventory: Add/edit/archive/feature products (`LogActivity` on Inventory module).
- Settings: Admin updates `tbl_payment_settings`, `tbl_meetup_settings`, `tbl_layaway_settings`.
- Orders/payments/deliveries/meetups: status transitions as above; activity log for logins (staff), order/payment/delivery/meetup actions.
- `GetActivityLogs` (ADMIN) reads `tbl_activity_logs`.

STEP 3: DETECT INCONSISTENCIES
--------------------------------------------------
- Documentation vs code – `OrderStatus.AwaitingMeetup` exists in constants but no assignment found in C#; meetup path uses `Ready for Meetup` instead.
- `OrderLifecycleRules` allows transitions to `Pending Payment` / `Pending Downpayment` from `Awaiting Payment Verification`, but `UpdatePaymentStatus` on REJECTED keeps order status as `Awaiting Payment Verification`; those pending states appear only in deadline/UI checks unless legacy data exists.
- SQL `CreateTables_And_Seed.sql` header/comments list shorter order/payment status sets than `OrderStatus` / actual controller behavior.
- `tbl_users.auth_provider` exists in SQL (LOCAL | GOOGLE) but is not on `tblUsersModel`; EF will not read/write it unless mapped.
- `tbl_products.image_id` has SQL FK; EF `tblProductsMap` does not define `HasOptional` to `tbl_images` (no navigation on product).
- `tbl_carts` / `tbl_cart_items` / `tbl_activity_logs` have SQL FKs to users (and carts) but EF maps omit navigations; relationship diagrams should still show DB FKs.
- `CreateOrder` does not clear the buyer’s cart server-side; docs often assume checkout empties cart.
- `tbl_order_items.product_id` is nullable with ON DELETE SET NULL in SQL; line items can orphan from product while retaining snapshot fields.
- `PaymentStatus.Pending` vs payment rows defaulting to SUBMITTED in SQL script vs always SUBMITTED on submit in app – align dictionary with actual insert path.
- `tblMeetupOutcomeMap` uses `WillCascadeOnDelete(true)` on order; multiple outcome rows per order are allowed by schema—documentation should reflect 1:M history, not 1:1.
- Redundant/overlapping concepts: `order.IsLayaway` vs `payment_type == LAYAWAY`; `order.MeetupDatetime` vs `tbl_payments.meetup_datetime`; meetup detection also uses payment flags in verification.
