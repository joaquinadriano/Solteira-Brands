Payment Deadline System - Design Notes (Before Implementation)
Repository: Solteira-Brands (ASP.NET + C# + MySQL)

Purpose
- Add a production-ready payment deadline system for both:
  1) Regular orders: deadline = 24 hours from order creation
  2) Layaway orders: deadline = monthly schedule based on installments
- Automatically cancel overdue unpaid orders via a background job.
- Restore stock when an order is cancelled/expired due to non-payment (and do so safely/idempotently).
- Do not break or change existing order/payment flow more than necessary.

Current Business Assumptions (to confirm in code)
1) When does inventory get deducted/reserved today?
   - Option A: Stock is deducted at order creation time.
   - Option B: Stock is deducted only when payment is confirmed (Paid).
   - Option C: Stock is “reserved” (deducted from available) and may be released later.
Decision impact:
- If stock is deducted/reserved at order creation, we MUST restore stock when we cancel/expire unpaid orders.
- If stock is only deducted on Paid, no stock restore is needed for unpaid cancellations.

2) What is the current fulfillment model?
   - Are items fulfilled only after full Paid status?
   - For layaway: are items fulfilled at the end only (common), or progressively per installment?
Decision impact:
- If fulfillment only happens after Paid, then on layaway default/cancel we should release stock back.
- If fulfillment happens per-installment, stock restoration rules need to release only the unfulfilled portion.

Key Data Model Changes (Database)
Add the following columns to the Orders table (names to match your schema conventions):
1) PaymentDeadline (DATETIME)
2) OrderStatus (e.g. Pending, Paid, Cancelled, Expired)
3) CancellationReason (nullable)

Recommended additional internal fields (not required by user, but important for correctness)
- StockReleasedAt / InventoryReleased (boolean or datetime)
- OR an inventory ledger approach (preferred in scalable systems)
Reason:
- Background jobs and admin actions can run multiple times; we must prevent double restoration.

Order Status Transition Rules (to avoid double-processing)
Treat auto-cancellation as a state transition guarded by:
- Current status must be Pending (or whatever your “unpaid” state is)
- Payment must not be marked as completed
- PaymentDeadline must be in the past (<= now)
Then:
- Pending -> Cancelled (with reason)
Optionally:
- Pending -> Expired (with reason)

Stock restore must happen ONLY on the successful transition that first marks the order as cancelled/expired.

Regular Orders Logic
When a regular order is created:
- PaymentDeadline = OrderCreatedAt + 24 hours
- OrderStatus = Pending (unless you currently set something else)

Layaway Orders Logic
When a layaway order is created:
- PaymentDeadline must represent the FIRST installment due date.

Monthly schedule calculation (needs a clear rule, propose one):
- Rule Proposal (simple and deterministic):
  - firstDeadline = OrderCreatedAt.AddMonths(1) using the same time-of-day
  - subsequent deadlines = previousDeadline.AddMonths(1)
- Alternative rule (also common):
  - firstDeadline = end of next month
  - subsequent = end of each month
To avoid ambiguity: choose ONE consistent rule and implement it everywhere (creation + after each successful installment payment).

After each successful layaway payment:
- Generate next PaymentDeadline = current PaymentDeadline.AddMonths(1)
- If you track installment count, when the last installment is paid:
  - Set OrderStatus = Paid (or your existing equivalent)

If user misses a layaway deadline:
- Configurable behavior (as requested):
  - Behavior Option 1: Cancel order (OrderStatus=Cancelled)
  - Behavior Option 2: Mark as defaulted (and optionally add a Defaulted OrderStatus value)

For inventory restore:
- If no fulfillment has occurred yet (typical), restore the full reserved stock on cancellation/default.
- If partial fulfillment occurred, restore only the remaining/unfulfilled portion (requires confirmation).

Background / Scheduled Auto-Cancellation
Goal:
- Periodically find orders that are overdue and unpaid.
- Update their status and cancellation reason.
- Restore stock exactly once (only on actual state transition).

Best Approach in ASP.NET (recommendation)
Use a durable job scheduler so it survives app restarts and avoids overlapping executions:
- Option A (recommended if available): Hangfire
  - Pros: persistent storage, retries, dashboard, easy recurring jobs.
  - Implementation: recurring job every N minutes to scan overdue orders.
- Option B: Quartz.NET with persistent store.
- Option C: hosted service + timer (only acceptable if you’re OK with restart risk and potential missed windows).
- Option D: external Windows Task Scheduler running a console job.

Even if we choose Hangfire/Quartz/hosted service, the core logic must be idempotent.

Idempotency / Concurrency Strategy (critical for production)
Do the overdue cancellation as a single atomic update guarded by conditions:
- WHERE:
  - OrderStatus = 'Pending'
  - PaymentDeadline <= nowUtc
  - (ensure payment is not recorded as completed if payment is tracked separately)
Then:
- Set OrderStatus = 'Cancelled' (or 'Expired')
- Set CancellationReason

After the atomic update:
- Only for orders whose status transition actually happened, restore stock.
- Restoration must also be idempotent or guaranteed to run once (e.g., by only running after the guarded transition).

Time Zone Handling (important)
- Store and compare deadlines in UTC.
- Display in the user’s local time (or site time zone).
- Use DateTime.UtcNow and UTC values in DB.
Note:
- Current requirement mentions DateTime.Now; we can keep semantics, but for production correctness we should migrate to UTC comparisons.

Buyer Side UI
On the order page (buyer side), display:
- Payment deadline (formatted date/time)
- Remaining time (countdown)
Implementation approach:
- Prefer JS real-time countdown using PaymentDeadline rendered into the page.
- Fallback:
  - if JS fails, show static “Time remaining: X” computed on server.
Safety:
- Countdown should not be security-critical (backend job enforces cancellation).
- If countdown shows expired, we can optionally disable the pay button, but still allow pay until backend cancels.

Admin Side UI
On admin payment management pages:
- Show PaymentDeadline
- Show OrderStatus
- Highlight overdue orders (e.g., Pending and PaymentDeadline <= now) with warning styling.
Also ensure:
- Admin manual cancellation uses the SAME cancel routine that triggers stock restoration.

Stock Restoration Requirements (explicit)
When an order is cancelled/expired due to payment deadline:
- Restore stock back to inventory availability.
- Do it safely:
  - No double-restoration if job runs again or if admin cancels after auto-cancel.
  - Must restore the correct quantity per order line item.

Implementation detail (proposed structure)
Centralize cancellation in one service method used by:
- Auto-cancellation background job
- Admin manual cancellation endpoint

Proposed internal API:
- CancelOrder(orderId, reason, cancelledBy, restoreStock: true)
Behavior:
- Start transaction
- Load current order status
- If not in Pending/unpaid state: no-op (do not restore stock)
- Update status + reason + cancellation timestamp
- Restore inventory for each order line item
- Commit

What we must verify before coding
1) Which table stores stock/inventory, and how “available quantity” is computed today.
2) Where stock is currently decremented/reserved (order creation vs payment success vs fulfillment).
3) How order line items are stored (so we can restore exact quantities).
4) If there is already a concept of order expiration or cancellation, and how it affects inventory today.
5) Whether payment completion is tracked in an orders table, payment table, or both.

Open Questions (to finalize rules before implementation)
1) Layaway first deadline rule:
   - Same time-of-day next month (proposal) OR end-of-month schedule OR custom day-of-month?
2) When a layaway installment is paid successfully:
   - do we just shift PaymentDeadline by +1 month, or do we also decrement remaining installment count?
3) Layaway default behavior:
   - cancel vs defaulted status (and do we want to add a Defaulted status value)?
4) Stock restoration on partial layaway:
   - is any fulfillment done before full payment? If yes, how much?
5) Deadline enforcement:
   - Should overdue orders be cancelled only when fully unpaid,
     or also if partial payments exist (typical behavior is cancel on any missed installment).
