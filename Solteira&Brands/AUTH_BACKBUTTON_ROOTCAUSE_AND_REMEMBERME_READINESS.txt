## Part 1 (Back button / auth-caching issue) — Analysis

### 1) Root cause of the back button issue
The most likely root cause is **browser caching / back-forward cache (bfcache) of previously rendered HTML for authenticated pages**.

What happens in your app:
- Users navigate to protected pages (examples: buyer cart/checkout/my orders; admin dashboards).
- The server renders those pages.
- On logout, the app **does** set no-cache headers on the logout response (in `AccountController.Logout()`), but:
  - The previously rendered authenticated GET responses may still be cached client-side.
  - When the user clicks **Back**, the browser may display the cached DOM/HTML snapshot **without making a new request**, so:
    - The server does not re-run `[Authorize]` / `[BuyerAuthorize]`.
    - The cookie/principal change (Buyer -> Manager) is not re-evaluated for the cached page snapshot.

Evidence from repo:
- `AccountController.Logout()` sets `Response.Cache.SetCacheability(HttpCacheability.NoCache)`, `SetNoStore()`, plus `Cache-Control` and `Pragma` headers.
- A project-wide search indicates **cache headers are not being applied consistently to all protected pages**; protected GET endpoints generally lack no-store/no-cache.

Net effect:
- Back button can show the **old account’s page snapshot** even though authorization would be correct on a fresh request.

### 2) Protected pages: Are all protected actions decorated?
Most authenticated pages appear to be correctly decorated:
- `SolteiraAndBrandsController` uses:
  - `[Authorize(Roles="ADMIN,MANAGER,STAFF")]` etc for admin/staff
  - `[BuyerAuthorize]` (custom attribute inheriting `AuthorizeAttribute`, effectively `Roles="BUYER"`) for buyer pages
- `AccountController` uses `[Authorize]` on profile/settings/actions.

However, there are a few sensitive endpoints that are **missing `[Authorize]`** entirely:
- `SolteiraAndBrandsController.UploadProductImage` (POST) — no `[Authorize]`
- `SolteiraAndBrandsController.GetProductImage` (GET) — no `[Authorize]`
- `AccountController.SeedTrialPasswords` (GET) — no `[Authorize]` (it resets trial passwords)

These missing attributes are separate hardening gaps, but the primary back-button symptom is best addressed by **cache-control on protected responses**.

### 3) Cache-control: which controllers/actions currently send cache headers?
- Cache-control / no-store headers are currently set on **logout** in:
  - `AccountController.Logout()`
- There is no evidence (from repo grep) of a consistent “protected responses are never cached” rule/filter across the rest of the app.

### 4) Minimal SAFE FIX (what to change)
Goal: prevent cached authenticated pages from being shown via Back, while not affecting public pages.

Approach:
- Add a reusable filter/attribute that sets:
  - `Cache-Control: no-cache, no-store, must-revalidate`
  - `Pragma: no-cache`
  - `Expires` in the past
  - (and corresponding `Response.Cache` calls)
- Apply it **only** when the request is for an action/controller marked as protected:
  - has `[Authorize]` or `[BuyerAuthorize]`
  - does NOT have `[AllowAnonymous]`
- Apply it for **GET/HEAD** only (back button behavior is mainly GET rendering).

Implementation pattern (minimal/no rewrites):
- Create `NoCacheForAuthorizedAttribute : ActionFilterAttribute`
  - In `OnResultExecuting`, check `filterContext.ActionDescriptor` attributes for:
    - presence of any `AuthorizeAttribute` (your `BuyerAuthorizeAttribute` inherits `AuthorizeAttribute`)
    - absence of `AllowAnonymousAttribute`
  - If protected + (GET/HEAD), set no-cache headers and `return`.
- Register globally via `FilterConfig.RegisterGlobalFilters(...)` so you do not need to modify every action.
  - Since the filter no-ops on public actions, it meets your “apply ONLY to authenticated/protected pages” constraint.

Additionally (authorization hardening gaps):
- Add minimal `[Authorize]` annotations only where missing:
  - `UploadProductImage`: add `[Authorize(Roles="ADMIN,MANAGER,STAFF")]` (or stricter if only admins should upload)
  - `GetProductImage`: add the same role restriction used for UploadProductImage
  - `SeedTrialPasswords`: optionally add `[Authorize(Roles="ADMIN")]` to prevent anonymous resets

### 5) Ensure server-side validation happens on every request
The cache-control fix ensures that Back navigation causes the browser to fetch protected pages again.
Then server-side authorization applies normally via:
- `[Authorize]` for admin/staff
- `[BuyerAuthorize]` for buyer-only areas
- `Application_AuthenticateRequest` principal population from FormsAuth cookie

Optional extra hardening (safe/minimal):
- `Global.asax.cs` currently decrypts the ticket and sets `HttpContext.Current.User` without verifying `ticket.Expiration`.
- For extra safety, check expiration there and clear/sign-out on expired tickets.
  - This prevents any “expired-but-still-present cookie” edge cases from being treated as authenticated in MVC.

### 6) Expected result
After logout and re-login as a different user:
- Back button must not reveal the prior user’s protected page snapshot.
- The browser will either:
  - show a login/unauthorized redirect, or
  - re-render the correct page based on the new authentication state.

### 7) Affected controllers/actions (summary)
With the global filter approach, the “NoCache” behavior applies to any action that is already protected via attributes:
- `AccountController`
  - actions already decorated with `[Authorize]` (settings/profile/change password/etc.)
- `SolteiraAndBrandsController`
  - all admin/staff `[Authorize(Roles=...)]` view/JSON endpoints
  - all buyer `[BuyerAuthorize]` view/JSON endpoints

Also affected by explicit `[Authorize]` hardening additions:
- `SolteiraAndBrandsController.UploadProductImage` (missing authorize)
- `SolteiraAndBrandsController.GetProductImage` (missing authorize)
- `AccountController.SeedTrialPasswords` (currently anonymous; recommended hardening)

## Part 2 (Remember Me) — Analysis only (DO NOT IMPLEMENT YET)

### 1) Does current login support persistent cookies?
No.
Current behavior:
- `AccountController.IssueAuthCookie(...)` creates a `FormsAuthenticationTicket` with:
  - `isPersistent: false`
  - expiration around 60 minutes (`DateTime.UtcNow.AddMinutes(60)`)
- Therefore the cookie is not persisted beyond the session cookie behavior.

### 2) Is there existing “Remember Me” logic in UI/controller/JS?
No.
Current login view:
- `Views/SolteiraBrandsAccount/SolteiraBrandsLogin.cshtml` contains username/password inputs only.
- No “Remember Me” checkbox exists.
Current JS:
- `Scripts/SBScripts/Service.js` -> `login()` sends only `username` and `password` to `/Account/Login`.
Current controller:
- `AccountController.Login(string username, string password)` signature does not accept `rememberMe`.

### 3) What is missing to support a safe Remember Me feature
To implement remember-me safely (without breaking existing cookie/login/logout/roles), the following are required:

UI:
- Add a checkbox:
  - unchecked by default
  - bound to an Angular model (`loginData.rememberMe`)

Client -> server:
- Update `Service.js` login() to send `rememberMe` to `/Account/Login`.

Server:
- Update `AccountController.Login(...)` to accept `bool rememberMe`.
- Update `IssueAuthCookie(...)` to support two modes:
  - `rememberMe=false`: keep current non-persistent behavior exactly
  - `rememberMe=true`: issue a **persistent** Forms auth ticket cookie:
    - `isPersistent: true`
    - expiration set to a configurable range (7–30 days)
    - set cookie flags:
      - `HttpOnly=true`
      - `Secure=true` when HTTPS
      - `SameSite=Lax` (or Strict) if supported by your target framework

Session interaction (your 15-minute inactivity rule):
- Your app’s login state is cookie-based, not Session-based.
- So “15 minutes of inactivity” remains as-is for session-only features; cookie persistence just means the user can be re-authenticated automatically when Session ends.
- If you need the exact “re-authenticate when session expires but persistent cookie exists”, you must ensure:
  - every request still uses the cookie-derived principal
  - and that the cookie expiration is checked correctly (see optional expiration hardening above)

Logout:
- Must clear both:
  - Forms auth cookie (already via `FormsAuthentication.SignOut()`)
  - any persistent remember-me cookie (if it reuses the same Forms cookie name, `SignOut()` should clear it; otherwise clear explicitly)

Edge cases:
- Expired cookie: reject/clear and redirect to login (no loops)
- Tampered cookie: decrypt failure should keep user unauthenticated (already handled by the catch in Global.asax)
- Avoid infinite redirects: ensure expired/invalid cookie is cleared before relying on `[Authorize]`

### 4) Where those changes would go (files/methods)
Not implementing now; these are the integration points:
- `Views/SolteiraBrandsAccount/SolteiraBrandsLogin.cshtml`:
  - add the checkbox + Angular binding
- `Scripts/SBScripts/Controller.js`:
  - add `rememberMe` to `$scope.loginData`
  - pass it through login action flow
- `Scripts/SBScripts/Service.js`:
  - extend `login()` to send `rememberMe` to `/Account/Login`
- `Controllers/AccountController.cs`:
  - update `Login(...)` signature to accept `rememberMe`
  - update `IssueAuthCookie(...)` to choose persistent vs non-persistent ticket
- `Global.asax.cs`:
  - optional hardening: validate ticket `Expiration` and clear expired cookie
- `Web.config`:
  - add `RememberMeDays` setting (used to clamp expiration to 7–30 days)

## Summary for documentation
- Back button issue is primarily caused by **client-side caching of authenticated HTML**.
- Safe minimal fix is to enforce **no-store/no-cache headers on protected GET/HEAD responses only**, via a global filter/attribute keyed off `[Authorize]` / `[BuyerAuthorize]`.
- Additionally, add missing `[Authorize]` attributes for a few sensitive endpoints (`UploadProductImage`, `GetProductImage`, and consider `SeedTrialPasswords`).
- Remember Me is not ready yet: current login uses **non-persistent** Forms auth tickets and there is no remember-me UI/JS/controller plumbing.
